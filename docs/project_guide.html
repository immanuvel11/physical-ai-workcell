A robot arm you can talk to, and how it works

You type “Put the red cube in the blue bin.” A simulated robot arm looks at the table with a camera, finds the cube, works out the moves, does them, checks with the camera that it worked, and stops if a person comes too close. This page explains every piece, from zero.

The idea in one minute

Factory robots today are usually programmed for one fixed job. An engineer “teaches” exact positions: the part is always here, the bin is always there. If a part arrives a few centimetres off, the robot grabs empty air. Changing the job means reprogramming.

This project builds a robot that does not need to be taught positions. Every time, it:

  1. Sees the table with a 3D camera and measures where everything is.
  2. Understands your instruction in plain language (with Claude, an AI model, or a simpler offline planner).
  3. Decides the order of moves: which part to pick, where to put it.
  4. Acts with the arm, avoiding collisions.
  5. Checks with the camera that it really worked, and fixes things if not.

All of this runs in a loop, connected through one shared “picture of the world”. That loop is the whole point of the challenge.

Everything is simulated. There is no real robot. The arm, camera, table and parts live inside Gazebo, a physics simulator. The same software could drive a real arm later; only the hardware connection changes.

One instruction, step by step

This is exactly what happens when you type “Put the red cube in the blue bin” in the control page. The grey labels are the states you see in the console as it works.

  1. you

    You type the instruction

    The control page at localhost:8080 sends your sentence to the executor, the part that runs the whole job from start to finish.

    Code: pai_ui/console.py → pai_planner/executor_node.py

  2. PERCEIVING

    The arm moves out of the way, the camera looks

    The arm folds back so it does not block the overhead camera. The camera gives a colour picture and a depth picture (how far away each pixel is). Anything sticking up from the table is an object. For each one the system measures position, size, rotation, colour and shape (box or cylinder). Big hollow things are bins, big flat things are trays.

    No AI model is trained here. It is pure geometry, so new objects work without retraining. It is accurate to about 1.5 mm and takes under a second.

    Code: pai_perception/segment.py, results stored by pai_world_model/world_model_node.py

  3. PLANNING

    The planner turns words into steps

    The planner gets your sentence plus the list of objects it can see. It answers with a short plan using only three allowed actions: pick, place, move_to. Here: pick(red_cube), then place(blue_bin).

    A validator then “dry-runs” the plan before anything moves: do these objects exist? Is the gripper empty before a pick? Is the target really a bin? If the instruction is unclear, the planner asks you instead of guessing.

    Code: pai_planner/planner.py

  4. EXECUTING

    The arm picks the cube

    The skill server turns “pick the red cube” into real arm motions. It moves above the cube, goes straight down, checks it really arrived, closes the gripper and lifts. MoveIt, the motion planning library, makes sure the arm does not hit the table, the bins or other parts on the way.

    Code: pai_skills/skill_server.py

  5. EXECUTING

    The arm places it in the bin

    It picks a free spot inside the bin (away from parts already there), lowers the cube, lets go gently and moves back up.

  6. VERIFYING

    It checks its own work

    The arm moves out of view again and the camera looks. Is the red cube actually in the blue bin now? The system never reports success it did not see.

  7. REPLANNING

    Only if something went wrong

    If the cube was not where expected (someone moved it), a grasp missed, or the path was blocked, it looks again and makes a new plan for the remaining work, up to 3 times. This is the “corrects itself while running” requirement.

  8. SUCCEEDED

    Done

    The console shows the result and the timings, typically about 30 seconds for one part.

The whole time, a separate safety program watches for people. If someone comes within 0.9 m the arm slows to 30 %. Within 0.45 m it stops, and it carries on by itself when they leave. The red E-STOP button stops it immediately.

The 12 building blocks

The project is split into 12 small programs (“packages”), each with one job. They live in ~/physical_ai_ws/src/. You do not need to read their code to understand the project; the table below is enough.

The worldpai_bringup

Starts everything with one command, and builds the simulated table, bins and parts from a settings file.

Like the power switch plus the stage set.

The worldpai_description

Describes the robot arm: its parts, joints, weights and gripper.

The robot’s blueprint.

The worldpai_moveit_config

Settings for MoveIt, the motion planning library: joint limits, which parts may touch.

The rulebook for how the arm may move.

Seeingpai_perception

Turns camera pictures into a list of objects with exact positions and sizes.

The eyes.

Seeingpai_world_model

Keeps the shared list of objects up to date: names stay the same between looks, and it tracks what is in the gripper.

The memory of where things are.

Decidingpai_planner

The planner (Claude or offline) and the executor that runs the look-plan-act-check loop.

The brain and the foreman.

Actingpai_skills

The three actions the robot can do: pick, place, move to a pose. Handles grasping details and retries.

The hands.

Safetypai_safety

Watches for people, slows or stops the arm, handles the e-stop. Also includes the simulated co-worker.

The safety officer.

Youpai_ui

The control page in your browser: instruction box, camera views, plan, E-STOP.

The dashboard.

Sharedpai_interfaces

Defines the messages the programs send each other, such as “detected object” or “pick this”.

The common language.

Sharedpai_core

Small helpers everyone uses: geometry maths, the Claude connection, scene tools.

The shared toolbox.

Proofpai_benchmark

The tests, the “traditional robot” for comparison, and the benchmark that scores both.

The exam.

Words you will hear

ROS 2
“Robot Operating System”. Not an operating system really: a toolkit that lets many small robot programs run at once and talk to each other. Version: Humble.
Node
One running ROS program, for example the perception node or the safety node.
Topic
A channel where a node broadcasts messages continuously, like a radio station. The camera publishes pictures on a topic.
Action
A request that takes time and reports progress, like “pick the red cube”. You can cancel it midway.
Service
A quick question-and-answer between nodes, like “look at the table now”.
Gazebo
The physics simulator that contains the virtual robot, camera, table and parts.
MoveIt
A library that plans arm movements that do not hit anything.
Panda
The robot arm model used: a Franka Emika Panda, a common 7-joint research arm with a two-finger gripper.
URDF
A file describing the robot’s shape, joints and limits.
TF
The system that tracks where every part of the robot and camera is in space, all the time.
TCP
“Tool centre point”: the spot between the fingertips. When we say “move the arm to X”, we mean move the TCP to X.
Depth camera
A camera that also measures distance for every pixel, so the robot gets 3D positions, not only a flat picture.
Scene graph
The shared list of what is on the table, where, and how things relate (“red cube in blue bin”).
Claude
The AI language model (by Anthropic) used as the planner. It reads your sentence and the object list and returns a plan. Needs an API key.
Rule planner
The offline backup planner. It understands simple sentences by keywords. Used when no API key is set.
API key
A password-like code that lets the program use Claude over the internet. You get it from console.anthropic.com.
Baseline
A “traditional” robot program used for comparison: fixed taught positions, no camera, no replanning.
Benchmark
The big test: many randomised scenes, both robots, scored on where the parts actually ended up.
E-stop
Emergency stop. Stops the arm at once until someone presses Reset.

How it stays safe

Safety does not depend on one trick. There are several layers, so if one misses something, another catches it.

  • WordsThe planner can only use 3 approved actions and objects it actually sees. It refuses to touch obstacles such as the coffee cup, and asks when an instruction is unclear.
  • Plan checkEvery plan is dry-run by the validator before the arm moves.
  • Work areaEvery target position must be inside a safe box over the table. Parts too wide for the gripper, or too deep in a bin, are refused.
  • CollisionsMoveIt plans around the table, bins and every part, with an extra safety margin around obstacles.
  • PeoplePerson within 0.9 m: slow to 30 %. Within 0.45 m: stop. Resumes by itself after they leave.
  • E-stopStops the arm in about 0.3 s (measured) and holds it until Reset.
  • Fail-safeIf the person sensor goes silent, or the safety program is not running, the arm does not move at all.
  • No blind movesIf the arm did not really arrive where it should be, it stops with an error instead of carrying on.
Honest note. This is a software safety layer for a prototype. A real factory needs certified safety hardware (safety scanners, a safety controller) doing the same jobs.

How to run it

Everything is in the folder ~/physical_ai_ws and is already built. Open a terminal and paste:

1. Start the robot world

cd ~/physical_ai_ws && source /opt/ros/humble/setup.bash && source install/setup.bash && ros2 launch pai_bringup bringup.launch.py rviz:=false

Wait 30–40 seconds until the Gazebo window shows the arm. Keep this terminal open.

2. Open the control page

In your browser, open http://localhost:8080. Click an example instruction and press Run. Watch the arm in Gazebo.

3. Stop

Press Ctrl+C in the terminal. Start again to reset the parts.

Optional: turn on Claude

Get an API key at console.anthropic.com, then run this once. It asks for the key without showing it:

mkdir -p ~/.config/pai && read -s -p "Anthropic API key: " k && echo "$k" > ~/.config/pai/anthropic_api_key && chmod 600 ~/.config/pai/anthropic_api_key && unset k

Restart step 1. The control page then says “claude planner”.

Explaining it to judges

The 30-second version.

“Traditional robots are taught fixed positions, so they fail when anything moves. Ours looks with a 3D camera every time, understands plain-language instructions, plans the moves, does them without collisions, and checks with the camera that it worked. If something changes mid-task it notices and re-plans. A safety layer slows and stops it near people. In 76 randomised trials it succeeded 84 % of the time, versus 16 % for a traditional taught program on the same robot, which only works in the exact layout it was taught.”

Questions they may ask

Did you train a neural network? On what data?

No task-specific training. Perception is geometry from the depth camera, so new objects work immediately. The planner is Claude, a general AI model used without retraining. Test scenes are generated automatically with random positions, lighting and clutter, and every run is logged, which can become training data later.

How is it “one pipeline” and not separate parts glued together?

Every part reads and writes the same shared world model, and one executor runs a closed loop: look, plan, act, check, re-plan. The check after every step is what connects the end back to the start.

How do you know it is not just lucky?

Results are scored on the simulator’s ground truth, not on what the robot believes. A trial only counts if every part ended up where it should and nothing else was knocked by more than 3 cm. The system reported “success” with a wrong end state zero times.

What happens if the AI makes a bad plan?

The AI never moves the arm directly. It can only choose from 3 approved actions and objects the camera actually measured. Every plan is dry-run by a validator first. If the plan is invalid it is sent back once for correction; otherwise it is refused.

Could this run on a real robot?

Yes, with a real arm driver and a real depth camera instead of the simulated ones. The planner, skills, world model and safety logic stay the same. Safety would need certified hardware for a real factory.

What it cannot do yet

  • Grasping is simplified. In the simulator, once a part is confirmed between the fingers it is “glued” to the hand, because the simulator’s finger physics is unreliable for small parts.
  • The person sensor is simulated. A real cell would use a safety laser scanner.
  • Only grabs from directly above. Parts deep inside a bin, or right next to a tall object, often cannot be reached.
  • Simple shapes. Perception assumes a flat table and box- or cylinder-like parts that are not stacked.
  • Claude is untested end to end in this setup until an API key is added. It needs internet and costs a few cents per plan.

Check yourself

Try to answer, then click to reveal.

What are the five steps of the loop?

See, understand, decide, act, check. In the console: PERCEIVING, PLANNING, EXECUTING, VERIFYING, and REPLANNING if needed.

Why does the arm move away before the camera looks?

So it does not block the camera’s view of the table.

What does the robot do if your instruction is ambiguous, like “the cylinder” when there are two?

It asks you which one, and does not move.

Why does the traditional robot fail in the “pose” test?

It grabs at the positions it was taught. When the parts are somewhere else, it grabs empty air.

What happens when a person comes within 0.45 m?

The arm stops. It continues by itself once the person has moved away.

Which part uses AI language understanding, and what does it need?

The planner, using Claude. It needs an API key; without one the offline rule planner is used.
