# Physical AI Workcell — Technical Report

From a plain-language instruction to a completed, verified pick-and-place task, as **one closed
loop** on ROS 2 Humble, Gazebo Fortress and MoveIt 2. This report covers what the challenge asks for:
the architecture, the models and software, the perception-to-action workflow, how data and
training are handled, the safety mechanisms, performance metrics, limitations, and how this scales to industry.
Measured results are in [`RESULTS.md`](RESULTS.md) (generated by the benchmark).

---

## 1. How the challenge requirements are met

| Requirement | How it is met | Evidence |
|---|---|---|
| Instruction → completed physical task as **one connected pipeline** | Every module reads/writes one shared world model (`/scene_graph` + MoveIt planning scene). The executor drives a perceive → plan → act → verify loop. | `pai_planner/executor_node.py`, system test A/B |
| Identify the relevant objects / work area | Class-agnostic RGB-D segmentation: anything above the table is found, measured in 3D (centre, size, yaw), named by colour + shape, and bins/trays are recognised. Claude vision can add semantic names. | Phase 3 test: 34/34, 1.5 mm mean position error |
| Understand spatial relations | Scene graph relations `in` / `on` / `near`, plus held object, are given to the planner and used for verification. | `pai_core/scene.py` |
| Work out the right sequence of moves | Claude turns instruction + scene graph into a schema-constrained plan over a small skill library; a validator dry-runs it before anything moves. | `pai_planner/planner.py`, unit tests |
| Carry it out safely with an actuator | Pick/Place/MoveTo skills on MoveIt 2 (collision-aware); safety supervisor scales speed / stops the arm. | Phase 2 test 12/12 ×5; system test F/G |
| Cope with real-world variation without reprogramming | Nothing is taught: positions come from perception every cycle; scenes are randomised in pose, lighting, clutter, and novel objects in the benchmark. | Benchmark conditions `pose`, `lighting`, `clutter`, `novel` |
| Handle tasks it was not set up for | Free-form language → Claude planner; unseen objects detected with no retraining. | Benchmark condition `novel` |
| Corrects itself while running | Every place is verified with fresh perception; failures (part moved, grasp missed, path blocked) trigger re-perception and re-planning of the remaining work; skills retry alternative grasps and placement spots. | System test C (part moved mid-task → re-planned → success) |
| Operates safely near people | Speed & separation monitoring, protective stop + auto resume, latched e-stop, fail-safe on sensor loss, workspace envelope, obstacles never picked, clarification instead of guessing. | System test F/G, §6 |
| Clearly outperforms a traditional rule-based setup | Same robot, same motion stack; the baseline is a taught, open-loop cell. Scored on simulator ground truth. | `RESULTS.md` |

## 3. Perception-to-action workflow (one instruction)

1. **Perceive.** The arm moves to `camera_clear`, then `/world_model/refresh`:
   - **Point cloud:** the depth image is back-projected and transformed to the world frame.
   - **Robot filter:** robot pixels are masked out using capsules along the arm's links (from TF).
   - **Segmentation:** anything 8 mm to 30 cm above the table is segmented into connected components.
   - **Receptacles:** segments with a footprint above 12 cm are receptacles. If the interior lies well below the rim it's a **bin**; if flat, a **tray**. Parts inside bins are split out by colour, parts on trays by height.
   - **Parts:** footprint, yaw and shape (box/cylinder) come from the **top face** (immune to perspective), height from the support surface. Colour is named relative to the table's brightness (robust to lighting).
   - **IDs:** the world model matches detections to existing tracks (same colour, nearest position; a just-placed part keeps its ID), computes relations, and pushes collision objects to MoveIt.
2. **Plan.** The executor sends `{instruction, scene, history}` to Claude:
   - **Output:** structured JSON (`output_config.format`) holding a status (`ok` / `clarify` / `impossible`), reasoning, an optional question, and steps over `pick` / `place` / `move_to`.
   - **Validation:** the validator symbolically executes the plan (IDs exist, only graspable parts, receptacle targets, gripper state consistent). Problems go back to Claude once for repair.
   - **Refusals:** server-side fallbacks (`fallbacks: "default"`) re-run a declined request on a recommended model.
   - **Offline fallback:** if Claude is unavailable, the rule planner is used.
3. **Act.** Each step goes to a skill.
   - **Pick:**
     - transit moves use Pilz point-to-point paths (short and predictable), falling back to OMPL only when the direct path is blocked;
     - closes across the part's narrow side, aiming for about 2.5 cm of finger overlap;
     - transits with the part still in the collision model, then removes it and descends in a straight line;
     - checks that the fingertip really arrived (within 3 mm), then closes and lifts;
     - tries equivalent grasps (±180°, ±90° for symmetric parts) if an approach is infeasible;
     - refuses parts too wide for the gripper or too deep inside a bin.
   - **Place:**
     - ranks free spots and hand yaws inside the receptacle, using clearance from the parts already there and the hand body's footprint;
     - lowers, releases and retreats, trying the next candidate if the straight-down approach is blocked.
4. **Verify.** After every place, re-perceive and check the relation `part in/on target`.
5. **Self-correct.** On any failure or failed verification:
   - re-perceive and re-plan the *remaining* work, with the history of what happened (up to 3 re-plans);
   - anything that moved in the meantime is picked up from its new position.

Typical timings (CPU-only laptop, simulation at real time):
- perception: about 0.8 s;
- rule planning: under 10 ms; Claude planning: a few seconds (network plus model);
- first motion: about 3 s after the instruction with the rule planner;
- one pick-and-place: about 25 s including verification.

## 4. AI models and software

| Component | Model / algorithm | Trained on task data? |
|---|---|---|
| Task planner | Claude (`claude-opus-5-5`) via the Anthropic Python SDK, JSON-schema structured output, effort `medium` | No: zero-shot, grounded in the live scene graph |
| Semantic labels (optional) | Claude vision on an annotated camera frame, cached per object | No |
| Object detection & 3D pose | Geometric RGB-D segmentation (OpenCV + NumPy), class-agnostic | No: no learned weights at all |
| Motion planning | MoveIt 2: Pilz PTP (deterministic point-to-point) first, OMPL RRTConnect as fallback, KDL IK, Cartesian paths | No |
| Control | ros2_control JointTrajectoryController, GripperActionController | No |

**Why this split.** The LLM does what needs world knowledge and language: interpreting
"crimson cube", "the kitting tray", resolving ambiguity and asking. Geometry does what needs
millimetres. The model never outputs coordinates or joint angles; it can only choose among
validated skills and object IDs that perception has actually measured. That keeps the system
explainable, auditable, and hard to talk into unsafe behaviour.

## 5. Datasets and training approach

- **No task-specific training.** Perception is analytic and the planner is a general-purpose
  foundation model used zero-shot. New objects, layouts and phrasings need **no data collection,
  labelling or retraining**. This is the core difference from a traditional cell and from
  detector-based pipelines that need a labelled dataset per part.
- **Evaluation data is generated, not collected.** `pai_benchmark/benchmark.py` is a seeded
  domain-randomisation generator. It produces scenes with random part poses and yaws, random
  light direction and intensity, distractor objects, moved obstacles, mid-task disturbances,
  unseen objects (from a pool parked off-table) and paraphrased instructions. Every trial is
  reproducible from `(condition, task, seed)`.
- **Ground truth** for scoring comes straight from Gazebo (`/world/workcell/dynamic_pose/info`),
  never from the system's own belief.
- **Logs as a future dataset.** Every run is appended to `~/.ros/pai/runs.jsonl`, recording the
  instruction, plan, planner, timings, re-plans and outcome. Together with ROS bags of the camera
  and joint streams, this is the raw material for later learning: fine-tuning a detector on
  real images, distilling plans into a small on-prem model, or imitation learning (e.g. ACT or
  diffusion policies via LeRobot) for contact-rich skills such as insertion.

## 6. Safety mechanisms (defence in depth)

| Layer | Mechanism | Where |
|---|---|---|
| Language | The planner may only use 3 skills and IDs that exist; obstacles and receptacles can't be picked; ambiguity → **ask, don't guess** | `planner.py` prompt + `validate()` |
| Plan | Symbolic dry-run of every plan before execution; invalid → repair once → refuse | `validate()` |
| Skill | TCP **workspace envelope** checked for every target; gripper-width check; deep-bin check | `skill_server.py` |
| Motion | Collision-aware planning against the live planning scene (table and bins exact; parts padded 1 cm, obstacles 2 cm); straight-line approaches collision-checked | MoveIt 2 |
| Motion integrity | A free-space move must really arrive (within 3 cm, one retry) before anything else happens. Straight-line moves are refused if they would go sideways by more than 3 cm, so a stuck or lagging arm can never turn an "approach" into a sweep across the table. Grasp orientation is chosen to keep the 22 cm hand body away from tall neighbours. In bins the fingers open only as far as needed. | `skill_server.py` |
| People | **Speed & separation monitoring**: person within 0.9 m → 30 % speed; within 0.45 m → protective stop, auto-resume after 1 s clear | `supervisor.py` |
| Mid-motion | On STOP/ESTOP the supervisor itself commands the arm controller to **hold at the current joint positions**, bypassing MoveIt and the skills, and repeats it at 5 Hz while stopped. Measured: arm moving at 1.2–1.5 rad/s halts in **0.28–0.36 s**. The skills treat this as an interruption and re-plan from the current state once allowed. A drop from NORMAL to SLOW cancels and re-plans at the lower speed. | `supervisor.py`, `_run_motion()` |
| E-stop | Latched until an explicit reset (console button, `/safety/estop`) | `supervisor.py`, console |
| Fail-safe | No person-sensor data for 1 s, robot pose unknown, or no supervisor heartbeat → **no motion** | supervisor + skill server (`require_safety`) |
| Verification | Every place is checked against fresh perception; the system never reports success it didn't observe | executor |
| World-model integrity | Perception only runs with the arm out of view (checked); segments touching the robot are discarded; new detections overlapping robot links are rejected. A phantom object on the robot would make every start state "in collision" and deadlock the cell. | `segment.py`, `world_model_node.py`, executor `_look()` |
| Start-up | No motion until all simulated grasp joints are released (otherwise parts welded to the hand could be dragged) | skill server |

Measured: a person walking up triggers SLOW then STOP and the arm halts; the task completes after
they leave. An e-stop during a fast move halts the arm in 0.28–0.36 s, it holds with no measurable
drift, and the motion completes after reset. (Earlier, cancelling through the MoveIt action took
more than 2 s. That is why the stop now goes straight to the controller.)

**Production note.** This is a software safety layer for a prototype. A deployed cell needs the
same functions in **safety-rated** hardware: a safety PLC or the robot's certified safety
controller, a safety laser scanner or light curtain (PL d / SIL 2), and a risk assessment under
ISO 10218-2 and ISO/TS 15066. The architecture maps onto that directly: the supervisor's zones
become the scanner's warning and protective fields.

## 7. Performance metrics

Measured by `ros2 run pai_benchmark benchmark` and summarised by `ros2 run pai_benchmark report`
(see `RESULTS.md`):

- **Success rate:** all goals hold in Gazebo afterwards *and* no other part was moved by more
  than 3 cm. Reported per system and condition.
- **Accuracy:** perception position error against ground truth (Phase 3 test) and goals achieved.
- **Response time:** planning time, time to first motion, total task time.
- **Robustness:** trials that needed re-planning, clarification rate, reported-success-but-wrong
  rate (the baseline's open-loop blind spot), safety stops.

## 8. Limitations (honest list)

- **Simulated grasping.** Finger-contact physics in Gazebo squeezes short, light parts out of the
  gripper. Once a part is confirmed between the fingers (by ground truth), the skill welds it to
  the hand with a detachable joint. On real hardware this block is absent and the real-gripper
  branch applies: close until the fingers stall, then check the final width.
- **Simulated person sensing.** People positions come from the simulator, standing in for a
  safety laser scanner.
- **Top-down grasps only.** No regrasping or tilted grasps. Parts deeper than the hand can
  reach inside an 8 cm bin are refused with a clear message. The Panda hand body is 22 cm long,
  so short parts standing within about 12 cm of a tall obstacle (the 10 cm cup, with its 2 cm
  safety margin) often can't be reached from above. The skill tries the best wrist angles first,
  then reports the failure.
- **Perception assumptions.** One calibrated overhead camera; a flat, known table plane; parts at
  least 8 mm tall; footprints are oriented boxes or discs; colours are coarse names; heavy
  occlusion or stacked parts aren't handled.
- **Approximate robot dynamics.** The Panda inertials are estimates (the upstream URDF has none).
  The arm is position-controlled, so this mostly affects realism, not task results.
- **LLM dependency.** The Claude planner needs network access, adds seconds of latency per
  plan, and costs a few cents per plan. The offline rule planner keeps the cell working (with
  narrower language understanding) when the cloud is unavailable.
- **Single arm, single camera, CPU only.** No GPU-based perception models were used, by design,
  to fit the development laptop.
- **Safety is not certified.** See §6.

## 9. Scalability to industrial applications

- **Real robots.** Swap the ros2_control hardware plugin and the URDF (UR, Franka, ABB, KUKA and
  Fanuc all have ROS 2 drivers). Skills, planner, world model and safety logic are unchanged.
  Remove the sim grasp joints; the real-gripper branch is already implemented.
- **Real cameras.** Any RGB-D camera publishing `image`, `depth_image` and `camera_info`, plus a
  hand-eye / extrinsic calibration in TF. Perception is class-agnostic, so no retraining is needed for new parts.
- **New tasks.** Add a skill (e.g. `insert`, `inspect`, `open_drawer`) as one action server and one
  line in the planner's skill list. The language layer composes it with the rest automatically.
- **Multiple cells.** Each cell is a ROS 2 namespace or domain; the executor's action API and the
  JSON run logs integrate with MES/WMS via a ROS–OPC UA or REST bridge.
- **Cost and latency.** One Claude call per plan (and per re-plan): a few seconds, and roughly
  3k input + 1–2k output tokens, i.e. about US$0.03–0.05 per plan at Opus 5.5 list prices. Routine
  instructions could be cached or served by a smaller, cheaper model (`model` parameter of the
  executor), with the large model kept for novel or ambiguous requests.
- **Deployment.** Everything runs on a single CPU workstation today; the heaviest piece, Gazebo,
  isn't needed on a real cell.
